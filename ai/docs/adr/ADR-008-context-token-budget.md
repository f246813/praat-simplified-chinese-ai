# ADR-008: 上下文按 token 预算裁剪，而且裁剪要看得见

**日期：** 2026-09-21
**状态：** Accepted

## 背景

请求是拼出来的：系统提示 + 工具 schema（`tools=`）+ 对象列表 + 对话历史 +
用户这句话。可历史一直是「按条数」截的（`qwen.history_messages` 里的
`history[-8:]`），对象列表是整份塞进去的——**没有任何东西看着 token**。

实测本机的数字：`ctx-size` 8192；`TOOL_PLANNER_INSTRUCTIONS` ≈ 545 token；
36 个工具的 JSON schema ≈ 18 006 字符 ≈ 6 652 token；回答还要预留
`plan_max_tokens = 700`。也就是说**工具说明一个人就吃掉八成窗口**，再塞 8 条历史
必然超；超了之后 llama-server 要么直接报错、要么从头截断（把系统提示里的规则截掉
更糟）。用户看到的现象是「聊着聊着模型就忘了前面说过什么」，而且不知道是为什么。

## 决策

`chat.run_turn()` 先算一次预算，再按预算裁：

```
预算 = ctx − 工具 schema − 系统提示 − 用户这句话 − 回答预留 − 安全余量(200)
对象列表 ≤ 预算 / 3        # 它必须让模型看到「当前选中」（提示词第 6 条靠它）
剩下的给对话历史（trim_history 从最近往回留，只留从某句 user 开始的完整后段）
```

- `qwen.estimate_tokens()`：CJK 1 字 ≈ 1 token，其余 ≈ 4 字符 1 token（够用就行，
  真按词表算得拉一个 tokenizer，而本地只有 llama-server 的 HTTP 接口）；
- `qwen.trim_object_context()`：表头和「当前选中」一定留，省掉多少写进文本
  （`（对象列表一共 N 个…还有 M 个没列出。当前选中是 …）`）；
- 被裁掉的东西写进 `TurnOutcome.notes`，对话窗口显示成提示行：
  「对话太长：这一轮只带了最近 2 条历史（省掉更早的 6 条）。本机上下文窗口 8192，
  工具说明加系统提示约占 7 197 token——想多带历史可以在模型预设里把 context_tokens
  调大。」——**不静默**。

## 备选方案

| 方案 | 为什么不选 |
| --- | --- |
| 继续固定 8 条 + 整份对象列表 | 8192 的窗口下必然超；而且是静默超（用户无从知道） |
| 只按字符数砍 system prompt | 对象列表和历史上限各自独立，砍不出一个「整体装得下」的保证 |
| 把工具 schema 也裁了（少给几个工具） | 工具选择能力直接下降，代价比「少带两条历史」大得多；真要省得先精简描述（另一件事） |
| 调大 ctx 到 16384 | 这是本机 8 GB 显存下的预设选择，改它要用户点头；而且治不了「超了就静默截」这个问题 |
| 按 tokenizer 精确计数 | 多一条 HTTP 往返（`/tokenize`）或者拉依赖；估算误差远小于安全余量 |

## 后果

**好处**

- 不会再出现「静默超窗」：请求要么装得下，要么带着一句「省掉了什么」的说明；
- 长对象列表也不再挤掉历史（以前对象列表是不设上限的整份塞）；
- 预算数字是可见的：`verify_*` 和提示行都能看到「工具说明占了多少、还剩多少」。

**代价与风险**

- 本机现实是「历史预算只剩几十 token」，所以多轮对话基本带不了历史——这不是这条
  决策的缺陷，而是「**36 个工具的 schema ≈ 6.6k token**」这个事实被暴露出来了。
  真要改善得从两头着手：调大 `context_tokens`，或者精简工具说明（例如把
  `measure` 的 41 个参数 enum 换成分组）；
- 估算不等于真值（中英混排的偏差可能有 10–20%），所以留了 200 token 安全余量；
- 提示行本身也占 token（很短），只在真的裁过时才出现。
