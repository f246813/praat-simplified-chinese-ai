# ADR-004: 一轮请求 = 「规划 → 执行 → 回灌结果 → 再规划」的有界循环

**日期：** 2026-09-20
**状态：** Accepted

## 背景

原来一条用户消息只规划一次：模型选工具、填参数，脚本投给 Praat，结果**只给用户看**。
于是有两个毛病：

1. 模型的回答是**在执行之前**写好的（「查询中间时刻的第 2 共振峰带宽。」），它根本
   没看到数值，更讲不出结论；
2. 一句话里要多步才能完成的事（「量一下 VOT，然后在起浊音的地方加个边界」）只能
   让模型一次写完整脚本，风险高；而且工具报错（参数不合法、对象类型不对）会直接把
   整轮判死，用户只看到「处理失败」。

## 决策

`:func:`praat_ai.chat.run_turn`` 把一轮请求做成有界循环（`MAX_AGENT_ROUNDS = 3`）：

1. 模型用原生工具调用给出下一步（可以一次多个）；
2. 每个动作渲染成脚本、投给正在运行的 Praat、把结果（或失败原因）作为观察结果
   **回灌**（`role: tool` + `tool_call_id`）给模型；
3. 模型不再调工具时，它那句话就是回答——这时候它已经看过真实数值；
4. 到轮数上限或总步数上限（`MAX_AGENT_STEPS = 5`）时，收尾调一次「只要文字」的
   请求，保证用户总能拿到一句回答。

三个直接收益对应三件事：

- **A2 结果回灌**：回答里带得出数值（实测「这个声音的谐噪比」→「平均值是 100.33 dB，
  最高值是 103.19 dB」）；
- **A3 多步操作**：上一步的结果作为观察结果进入下一轮（实测「把当前声音的前 0.3 秒
  截出来，然后把它改名为 短音」→ 两步，并且知道新对象是 id 3）；
- **A4 工具报错当观察**：工具自己拒绝请求时不再抛给用户，而是回灌「工具 X 没有执行：
  共振峰编号只能是 1–20 的整数」，模型改参数重试（实测 VOT 的占位 0、共振峰编号
  越界都能自己纠正）。只有当模型确实同时给了脚本时，才用它那条脚本兜底，并在
  窗口里说明「改用模型给出的脚本」。

## 前提与防线

**必须给 llama-server 加 `--jinja`**：回灌用的是 `role: tool` 消息，只有让模型自带的
chat 模板处理它，小模型才不会跑偏。实测对照（同一台机器、同一个 Qwen3.5-2B）：

| 服务端 | 「阅读当前对象的信息」 | 「打开当前声音的编辑器」 |
| --- | --- | --- |
| 默认模板 | 节点数：3（做成频谱图 3 次，选错工具） | 3 步（编辑器 + 2 次频谱图） |
| `--jinja` | 1 步 `object_info`，第二轮直接回答 | 1 步 `view_edit`，第二轮直接回答 |

防线（都是被小模型的退化行为逼出来的，实测有效）：

- **同一动作只执行一次**：工具名 + 参数完全相同的重复调用只回灌「这一步刚才已经
  执行过」，不再动 Praat（实测「截取 0.2–0.5 秒」被连做三遍）；
- **总步数上限**：一次请求最多执行 5 个动作；
- **用户没说要第二步时，第二轮之后不许动对象**：会改动 Praat 里对象的工具
  （`tools.MUTATING_TOOLS`：建/删/改名/标注/另存/读入/频谱图/custom_script）在
  第二轮之后要执行，用户这句话里必须出现「然后 / 再 / 接着 / 之后 / 并且 / 同时 /
  顺便 / 先」之类的说法（`chat.wants_second_step`）；只读查询不受限制。实测 0.8B
  预设下「打开当前声音的编辑器」会在第二轮顺手做两次频谱图并把选中对象换掉，后面的
  请求全被带偏；
- **观察结果里带收尾提示**：每一步成功之后都明确告诉模型「够回答就直接回答，不要
  顺手多做别的操作」；
- **正文里的工具调用文本也要认**：模型偶尔把调用写成
  `<tool_call><function=…>` 塞在正文里（`qwen.parse_text_tool_calls`），以前那串 XML
  会被当成回答显示给用户；现在它会被解析成动作，XML 之外的文字才算回答。

护栏管得住「回灌之后多做」，管不住**第一轮就选错工具**——那是模型能力问题：2B 预设
实测每条请求都选对（`verify_chat_live.py` 六个用例全是 1 步、`verify_chat_planning.py`
21/21），0.8B 预设会把「阅读当前对象的信息」做成频谱图。日常用 2B 预设，0.8B 只用
在显存吃紧或者快问快答的场合。

## 备选方案

| 方案 | 为什么不选 |
| --- | --- |
| 保持「一轮规划」 | 回答讲不出数值，多步请求只能靠模型一次写完整脚本（`guide.md` §8.4 的老问题） |
| 不设上限的 ReAct 循环 | 小模型会一直调工具（实测退化），用户的 Praat 会被改花 |
| 每次都执行多个动作、只回灌一条合并结果 | 分不清哪一步失败、哪一步成功；A4 就没法让模型定点改参数 |
| 让模型自己判断要不要继续 | 它不知道自己"够不够"，所以要给明确的收尾提示 + 服务端 `--jinja` |

## 后果

**好处**

- 回答基于真实数值；多步请求能落地；工具报错能自愈；用户还能在窗口里看到每一轮
  干了什么（`第 N 轮：pitch（time=0.25）→ 基频（0.250 秒处）= 220.000 Hz`）。

**代价与风险**

- 每条请求至少两次模型调用（规划 + 回答），实测一次调用 0.3–1 秒；
- 循环里每一步都是一条独立的 app 消息（各有请求编号），Praat 被模态框挡住时会在
  某一步超时——那时把失败原因回灌给模型，它会解释而不是硬报错；
- `PRAAT_AI_PLANNER=json` 的兜底路只跑 2 轮（老接口没有 tool 消息的形状）。
