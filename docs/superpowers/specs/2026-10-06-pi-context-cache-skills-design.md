# AIPraat：借鉴 Pi 的上下文、缓存与技能架构设计

日期：2026-10-06。状态：设计完成，尚未实施。范围：现代前端的 Python 云端后端；本地模型、旧 Tk 窗口维持现有行为，后续适配共用接口时另行验证。

## 1. 设计结论

采用用户已经认可的“固定基础规则＋按任务加载技能＋保留代码 guard”，把 Pi 的机制移入现有 Python／Pydantic AI 后端：**会话拥有消息历史，任务拥有执行状态，阶段拥有请求配置，供应商适配器负责缓存字段与用量归一化。**

原来三点继续保留，但实施单位从“提示词字符串”提升为“最终 API 请求”：

| 原来三点 | 在 Pi 机制下的改进 | 最终决定 |
| --- | --- | --- |
| 固定请求前缀 | 同时固定阶段规则、工具声明顺序、输出协议和序列化方式；在供应商适配后检查真实请求 | 建立稳定请求构造器，动态内容只追加到消息尾部 |
| 保留真实消息历史 | 分开用户可见对话、SDK 原生消息和专业证据；保留工具调用与返回的配对 | 普通对话跨轮追加；规划与报告在各自任务内追加，压缩时开启新上下文版本 |
| 规划与报告分别优化 | 共享基础规则和正式对话，但分别管理工具、技能、预算、缓存统计和续写 | 接受阶段差异，不以跨阶段整段命中为目标；分别减少重建、冗余和无效请求 |

把提示词搬成 SKILL.md 主要改善维护和按需加载。它只有在减少实际输入、减少额外请求、稳定共同前缀时才会改善性能；文件名和 skill 格式本身不会提高缓存命中率。

方案选择：

| 方案 | 收益与代价 | 选择 |
| --- | --- | --- |
| 在现有 Python 后端采用 Pi 的会话／循环／适配器分层 | 保留 Pydantic AI、现有执行器、界面和 guard，逐项迁入可验证机制 | **采用** |
| 引入完整 Pi TypeScript 后端或 sidecar | 增加 IPC、依赖、消息协议迁移和两套取消／持久化生命周期 | 当前收益不足，暂缓 |
| 只把大提示词移到 skill 文件 | 可以整理规则，但 JSON 历史、动态系统提示和每轮连接关闭仍存在 | 作为整理步骤，不能替代架构改造 |

这里研究的是 [earendil-works/pi](https://github.com/earendil-works/pi)，研究提交固定为 **28dcce2ba45ce4a9efeb0f5b686f0be830fd89b9**。已有文档里的 PI-Desktop 是界面移植来源，两者的技术范围和许可不能混为一谈。

## 2. 当前实现与问题定位

以现有代码为准，不能把旧窗口的历史截断行为套到现代前端上。

| 当前实现 | 对性能／缓存的影响 | 对应文件 |
| --- | --- | --- |
| 规划输入顺序为当前目标、对象／范围、证据、JSON 对话；部分专用指导进入动态系统提示 | 新目标很早打断共同前缀，历史内容相同也难以复用 | [cloud_agent.py](../../../ai/praat_ai/cloud_agent.py) |
| Agent.iter 没有传跨轮 message_history；本次工具循环内部已有 SDK 消息 | 单次循环可以追加；跨轮仍在重建一大段文本历史 | 同上 |
| 普通对话、报告、压缩分别新建 Agent；报告有阶段专用输出类型和校验 | 需要独立阶段配置，但不必每次重建其静态规则和历史表示 | 同上、[modern_budget.py](../../../ai/praat_ai/modern_budget.py) |
| ModernStore 保存可见消息、摘要、证据；没有保存完整 SDK 原生消息链 | UI 状态和模型协议混用，无法直接恢复工具调用／返回配对 | [modern_store.py](../../../ai/praat_ai/modern_store.py) |
| 每轮把累计专业证据再拼成历史中的合成 user 消息 | 输入增长，已有证据重复注入，历史前缀容易重排 | [modern_app.py](../../../ai/praat_ai/modern_app.py) |
| 现代前端每次任务创建并关闭 CloudRuntime；runtime 自身已有配置身份与客户端复用能力 | 任务内复用存在，跨轮连接复用尚未成立 | [modern_execution.py](../../../ai/praat_ai/modern_execution.py)、[cloud_runtime.py](../../../ai/praat_ai/cloud_runtime.py) |
| 现代预算估算固定规划规则／全量工具和 JSON 历史；普通对话也经过这一入口 | 预算与实际阶段请求可能不同，导致过早压缩或阶段内预算不一致 | [modern_budget.py](../../../ai/praat_ai/modern_budget.py)、[escape_policy.py](../../../ai/praat_ai/escape_policy.py) |
| 已记录请求次数、首字、耗时、输入／输出／思考 token；没有完整缓存读写统计 | 无法判断缓存改善，也难以区分思考、连接、工具与预填充耗时 | [cloud_agent.py](../../../ai/praat_ai/cloud_agent.py) |

当前配置是百炼 qwen3.7-flash，配置的上下文预算为 32768，limit_tokens=false。32768 是应用配置预算，不代表从该模型名称查证出的服务商真实最大窗口。思考与输出预算的既有语义仍需保留。

现有 SSE 尾部排空和连接释放适配已经存在于 [cloud_stream.py](../../../ai/praat_ai/cloud_stream.py)，本设计复用它，不重写同类流式适配。

## 4. 目标架构与职责

~~~mermaid
flowchart TD
    UI[现代聊天界面] --> Session[SessionContext：正式对话与模型消息]
    Session --> Route[已有保守分流与任务快照]
    Route --> Builder[PhaseRequestBuilder：规则、技能、历史、预算]
    Builder --> Adapter[供应商适配器：最终请求与缓存统计]
    Adapter --> Model[云端模型]
    Model --> Guard[现有工具 guard]
    Guard --> Exec[串行 Praat 执行器]
    Exec --> Evidence[EvidenceStore：原始证据与投递事实]
    Evidence --> Builder
    Model --> ReportGuard[现有报告 guard：核对与自动修]
    ReportGuard --> Session
    Session --> UI
~~~

四个职责边界：

1. **SessionContext**：管理正式对话、阶段消息链、摘要边界和上下文版本；不执行工具。
2. **TaskState**：保留原始目标、对象身份／范围、投递状态、证据和失败计数；不因改写提示词而重新授权或重置。
3. **PhaseRequestBuilder**：按 dialogue／planner／report／summary 生成与预算一致的请求，固定基础规则、工具表和输出协议。
4. **ProviderAdapter**：在请求副本上添加已验证的供应商字段，捕获实际请求形状、usage 和传输时序；不解释 Praat 业务权限。

### 4.1 三种历史与一个证据仓

| 数据 | 保存内容 | 用途 |
| --- | --- | --- |
| 用户可见对话 | 用户输入、正式 assistant 回答、UI 状态与派生展示 | 界面／搜索／导出；不是完整模型协议 |
| 规范模型消息 | 完成的 ModelRequest／ModelResponse，工具 call_id、返回、重试关联和阶段信息 | 原生历史、任务内继续、供应商投影 |
| 摘要／上下文版本 | 被总结到的 seq、摘要、生成来源、版本及保留边界 | 压缩后的新请求；摘要明确标成历史摘要 |
| 完整专业证据 | 原始测量行、对象／范围／单位／来源、投递结果 | guard 核对和追溯；不由摘要覆盖 |

UI 的进度、思考卡片、临时正文、coverage 渲染不能再次作为 user 文本塞回历史。正式报告保存核对／自动修后的模型可见正文；展示表格等派生内容只在必要时投影一次。

阶段内的规范协议链保留模型实际返回的原始消息及 SDK 重试消息，不把 guard 修好的正文回写到既有 ModelResponse。核对后的正式回答另存为共享对话事件，供下一任务生成基线；本任务内续写仍沿用实际协议链。这样既保留校验后的正式内容，也避免重写旧响应打断本阶段的历史前缀。未通过校验的草稿可作为本任务修正上下文，不能进入下一任务的正式对话基线。

持久化采用 ModernStore 的增量迁移，建议增加 model_events 表或等效专用记录。最低字段：session_id、task_id、phase、context_epoch、seq、kind、status、协议版本和可恢复的 SDK 消息 payload；request_metrics 按逻辑请求与尝试号关联。模型／适配器／schema 版本变动时验证恢复兼容性，不能直接重放旧私有对象。

密钥不写入 payload；音频字节不写入数据库。临时附件引用恢复前检查是否仍可用，过期引用不能冒充可访问音频。旧会话只有可见消息的，迁移成正式 user／assistant 基线，不凭空补造历史 tool 事务。

流式草稿与执行事实独立保存：取消、网络断开或进程退出后，已投递事实仍保留；未完成回复不冒充正式答案。孤立工具调用不得直接放入新请求，恢复时只能根据真实执行日志补齐实际结果／中断状态，结果未知则保持 unknown，不自动重放操作。

### 4.2 阶段与会话范围

| 阶段 | 消息链范围 | 起始历史与后续追加 |
| --- | --- | --- |
| dialogue | 会话内、同一阶段配置与 context_epoch | 规范正式对话 → 本轮用户输入 → 模型正式回复；跨轮继续 |
| planner | 单个任务 | 起始正式对话快照 → 任务上下文／技能 → 目标 → 原生工具调用／返回；本任务内追加 |
| report | 单个任务及其修正／续写 | 起始正式对话快照 → 报告技能／证据 → 目标 → SDK 修正／续写消息；不复制规划阶段的原始工具协议 |
| summary | 单次压缩作业 | 被压缩消息的合法投影；仅返回摘要，不继承执行权限 |

新任务不会接着上一任务的工具调用链执行。规划和报告跨任务主要复用静态前缀与有序正式对话，避免为了缓存继承过期任务指令。阶段切换时从共享正式对话生成新基线，不把上一阶段的系统规则插进另一个阶段。

模型、阶段规则、工具 schema、输出 schema、知识权限等静态配置变更，或历史压缩／编辑／分支改变，开启新的 context_epoch。仅追加新目标／证据不必新建版本。会话标识用于应用追踪，只有供应商明确支持时才转换成 API 缓存相关字段。

## 5. 原来三点的具体优化

### 5.1 固定前缀：从字符串移到最终请求

每个阶段使用一个固定配置，按下列顺序构造：

~~~text
阶段固定 system：基础规则 + 阶段职责 + 固定技能索引
固定工具声明／输出协议：仅本阶段需要的集合，声明顺序不随任务变化
本阶段已有的合法消息历史：保持原顺序、原内容
新追加的任务指导：本次适用技能正文、对象／范围快照、相关证据
本轮用户目标
后续 assistant／tool 消息：按协议追加
~~~

这是应用的逻辑顺序；最终 system、tools 和输出 schema 的位置由适配器决定，必须在最终 wire request 上复核。不能只对传入 Agent 的 prompt 做哈希就宣布前缀稳定。

基础规则保留身份、能力范围、知识权限、证据与执行边界；阶段职责和 schema 固定。韵律、摆放等随目标变化的具体指导移到追加的任务指导；“有证据／无证据”等条件写成固定条件规则，不每轮换整段 system。用户目标仍单独保留在 TaskState，guard 不依赖模型复述后的目标。

对象 PID、当前选区、临时文件、失败详情、当前时间和新证据不能放进固定 system。运行时技能是应用选择的任务说明，内部使用有类型的 TaskGuidance 记录；当前 Chat Completions 路径投影成新追加的 user 文本块，明确标出“应用任务指导”、技能 id／版本和适用任务，避免中途 system 被适配器合并回前导规则。用户原话与工具数据单独标明来源，工具文本不能生成 TaskGuidance；最终动作仍由 TaskState 和代码 guard 校验。后续若改用其他消息角色，必须先验证最终请求不会改写既有前缀。

工具表按固定 schema 身份排序，JSON 对象序列化统一，数组保持语义顺序。动态任务只改变参数／消息，不能每次临时增删工具；普通对话工具表为空，规划阶段使用固定规划工具表。若今后缩小工具集，用显式配置版本，接受切换造成的缓存边界。

记录静态规则、工具、输出 schema 和逐消息摘要指纹，诊断首次变化的位置；真实请求正文仅在受控离线测试中捕获，常规日志保存摘要与长度。内容指纹排除请求局部的缓存标记，同时另记标记位置；不能把合法的标记移动误报成历史内容变化。指纹只能解释客户端变化，不能证明服务端缓存淘汰／路由的原因。

### 5.2 原生历史：追加、证据投影与压缩

普通对话使用 SDK 原生历史，停止把整个历史 JSON 放进一个 user 消息。规划／报告继续使用各自合法的 SDK 消息链，修正和截断续写携带必要原生上下文，不另造一个脱离任务的小提示词。

压缩请求也使用真实角色投影；目前 text_request 把消息列表 JSON 整体传成单个 user 的做法一并替换。只存一次用户输入、一次正式回复，避免 UI 渲染、JSON 快照和原生消息三份重复进入模型。

证据投影分为三层：

- **原件**：完整记录一直存证据仓，guard 按原件核对。
- **模型需要的证据**：明确保留证据编号、对象身份、范围、量名、单位、值和来源；本轮相关测量优先完整给出。
- **历史索引**：较早且无关的详情用稳定编号和简短描述；需要重用时由应用根据任务关联补入，不依赖模型凭摘要恢复数字。

同一阶段消息链里已给过的证据不每轮再把全仓库拼一次。新任务／新版本生成起始证据快照，之后只追加新增证据或明确修订；引用旧编号必须能解析到原件。证据选择无法确认时保守保留相关原文，不能为节省 token 静默删掉核对依据。

统一阶段预算：估算最终请求的 system、tools、schema、历史、任务指导、证据和附件；结合最近同一配置／投影下的 provider usage 与新增内容估算。不能把不同阶段的 token 数直接拿来当当前请求大小。

~~~text
可用输入 = 配置／查证的上下文上限
         − 当前输出与思考预留
         − 明确的协议／估算余量
~~~

输出与思考的包含关系按供应商归一化，避免重复扣除；保留 token_mode、thinking_level 和 force_deep_thinking 的原有含义。缺少可靠模型窗口元数据时继续使用明确配置，不由模型名称猜测。

预算紧张才压缩：优先旧正式对话，保留完整最近交互／工具事务，摘要不得替代专业证据。摘要完成后开启新版本，预计缓存会重建并记录 compression 原因；复核仍超窗则沿用清晰错误，不循环付费总结或静默删测量。近期保留量按实际窗口和任务预算计算，不照搬 Pi 的大窗口常量。

summary 不申请额外显式缓存写入；百炼隐式缓存无法关闭，因此“摘要不写缓存”只能表示不发送显式标记，不能保证服务端完全不缓存。

### 5.3 阶段独立优化：分别缩小请求与重试成本

| 阶段 | 优化重点 | 保持的语义 |
| --- | --- | --- |
| dialogue | 无工具／无对象初始化；长期追加历史；按其真实请求预算，避免按规划工具表压缩 | 普通回复仍逐段展示；未知／具体材料问题不误分流 |
| planner | 固定工具表；任务内追加；新目标放尾部；同对象多参数优先复用既有 measure 能力 | 工具 guard、原对象／范围绑定、投递顺序与结果核对 |
| report | 固定报告协议／条件规则；只给相关证据和真实投递事实；原生修正／续写 | 七项报告闸门和七项自动修；未验证正文不进入正式历史 |
| summary | 轻量独立职责，不带 Praat 工具／整套报告 schema；只压缩允许总结的历史 | 摘要不是测量证据，原记录不删除 |

规划与报告共享基础规则的维护来源，但在请求中使用阶段配置；报告不靠继承规划 Agent 获得执行工具。无需为了追求跨阶段整段缓存命中把两个阶段合并成一个带全部权限的 Agent。

沿用现有保守分流，技能选择不再额外调用模型分类。明确时长快路继续零模型请求；普通对话正常完成一请求。减少往返优先使用现有多参数测量，后续并行仅开放给经证明不共享 Praat 状态的独立计算。

### 5.4 追加需求：缺少发音说明时使用文件名线索

**没有可用发音词典，且用户在本轮或已保留的明确说明中未指定当前录音的词句／音节／音素／发音时，允许根据当前目标录音的原始文件名获取发音相关信息。** 这是一项任务元数据回退，不新增识别模型或模型请求。

优先采用用户明确说明，再使用词典支持的信息；只有两者都缺少时启用文件名线索。用户后来补充或纠正内容时，追加新说明并覆盖先前候选，不让文件名推测继续影响结论。

使用与当前录音绑定的原始文件名，去除扩展名、明确的录制序号等非内容部分；可提取词句、音节、音标或明确的语言／声调标签。例如“こんにちは_take2.wav”可提供候选文本“こんにちは”；“recording_001.wav”没有明确发音内容，沿用既有的信息不足处理。临时导出文件、内部请求编号和其他录音的文件名不作为线索来源。

在 TaskMaterials 的来源元数据中保存原始文件名、候选信息、source=filename 和“根据文件名推测”状态，按当前录音绑定后作为新任务上下文追加到规划／报告输入。文件名不冒充用户自述，不写进固定 system；不额外调用模型做文件名分类。材料来源保留原始名称，避免音频转换／导出后只剩临时文件名。

报告使用该信息时简短注明“根据文件名推测”。候选表示可能的录音内容，不能单凭名称断言录音实际读了什么、发音是否正确或声学数值；文件名里的序号／声调标签也不当作实测数字。多个候选或语言不明时保留不确定性，不强行补齐标准读音、词典条目或音素序列。

## 6. 技能如何放入项目

区分两个使用者，避免把开发技能当成产品运行规则：

| 类型 | 建议位置 | 谁加载 | 内容 |
| --- | --- | --- | --- |
| 项目开发用缓存技能 | .agents/skills/aipraat-prompt-cache/SKILL.md | 支持该目录的开发代理 | 固定前缀审计、最终请求三轮对比、缓存用量检查、压缩／TTL／配置变化的区分 |
| AIPraat 运行时任务技能 | ai/skills/&lt;skill-id&gt;/SKILL.md | 本项目 SkillRegistry／RequestBuilder | Praat 任务的专业操作与报告指导 |
| 始终存在的基础规则 | ai/praat_ai 的统一规则来源 | 各阶段 builder | 身份、证据与权限边界；代码校验继续独立 |

开发 skill 的目录是拟定布局，落地时按项目使用的开发代理确认发现规则；产品不扫描该目录。运行时技能由产品加载，不能靠 Codex 自动发现代替实现。

首次迁入仅拆出现有随任务变化的指导：韵律证据／结论、对象与时间范围摆放、失败后的报告收尾。使用已有目标／阶段／状态判据选取，不新建泛化语义路由器；新增行为限于第 5.4 节已明确的文件名线索回退。未匹配仍走原来的基础能力。

每个运行时 skill 包含 id、描述、适用阶段、版本、来源及正文。索引固定且简短；正文在本任务需要时由应用本地加载并作为新增指导消息注入。同任务已加载同版本不重复注入；版本变化在任务边界生效，正在执行的任务继续使用其快照。热切换不能悄悄重写已有 system。

用户明确改变任务时允许追加新技能，保留旧指导的任务边界说明；下一新任务重新选择，避免无关技能永久堆在规划链上。技能不含密钥，不执行任意脚本，不改变工具权限；其脚本／参考文件需要单独的现有执行路径。

[OnlyTerp/prompt-cache-skills](https://github.com/OnlyTerp/prompt-cache-skills/tree/5b58ae26bd446bfb2eee97e8dad076ffb46a6715) 用作开发技能的参考，吸收“最终请求核对、易变字段移尾、三轮缓存阶梯验证”。仓库里的 Cline 专用修复不直接当成本项目补丁；缓存标记在请求 N 建立、请求 N+1 命中是正常情况，不能把“标记在最后一条消息”一概判成缓存错误。本轮只定义项目技能的放置与职责，不下载或安装第三方 skill。

## 7. 供应商缓存、连接与观测

### 7.1 百炼适配策略

初期默认 implicit，先验证稳定前缀；再增加能力已确认的 explicit 模式进行对照。按模型、接口、地域记录支持情况，不因为 URL 兼容 OpenAI 就启用同样参数。

截至研究日，百炼官方列出 qwen3.7-flash 支持上下文缓存。隐式自动启用、不可关闭、命中不保证；显式在消息 content 块上加 ephemeral 标记，最少 1024 token、最多四个标记、有效期五分钟且命中重置，向前查找最多二十个 content 块；两种模式单请求互斥，首次创建需等响应完成后再复测。[百炼官方缓存说明](https://help.aliyun.com/zh/model-studio/context-cache)。

explicit 在最终请求副本上标记稳定文本边界，并按对话追加选择增长边界；不把缓存字段写回规范消息。先验证稳定文本，工具声明标记、音频内容缓存及非官方网关不靠类推开启。标记位置应符合供应商回溯限制，不能只在无限增长历史最后一块加标记后假设一定命中。

显式模式包含缓存创建成本。单轮／间隔较长任务未必更省，开启依据是同样任务序列的实际费用与耗时；不为了命中率发送付费保活请求，也不增加隐藏预热调用。短请求无需凑到缓存门槛。

### 7.2 runtime 生命周期与执行速度

现代应用负责持有会话级 CloudRuntime，复用事件循环和 HTTP 客户端。配置身份继续包含地址、模型、凭据和超时；身份变化关闭旧客户端，前端关闭／会话删除释放对应资源。连接身份仅在内存比较，持久日志不保存原始凭据。

取消只影响其所属任务；已经显示的正文不能通过透明重试再次混入。保留 SSE 收尾和异常处理。单个 runtime 的串行 gate 不得变成跨会话全局瓶颈；云端等待可以独立，真正访问 Praat 的步骤仍受已有共享锁保护。

连接复用减少建连开销，不等于缓存命中；稳定前缀减少预填充重复，不保证输出解码／深度思考变快。基准固定同样的思考档、输出预算和音频条件，不能通过降思考制造“架构提速”。

### 7.3 必需指标

每次实际请求记录 phase、session/task/context_epoch、逻辑请求号、attempt、请求原因、耗时、首个可见文本时间、HTTP／结束状态和实际 usage；整任务汇总请求数、工具耗时、报告重试与 guard 计数。缓存读／写／总输入保留供应商字段来源和归一化语义。

~~~text
缓存覆盖率 = Σ cache_read_tokens / Σ input_tokens_total
缓存命中请求率 = cache_read_tokens > 0 的请求数 / 可观测请求数
~~~

分别报 dialogue、planner、report、summary 的冷启动／连续追加／压缩后数据。字段缺失记 null／unreported，不能填零冒充观测。若供应商输入 token 已包含缓存读写，不再次相加；如果提供未缓存输入，再与读写相加恢复总输入。思考 token 是否包含在输出同样按供应商字段定义。

raw usage 仅保存计数相关字段；聚合按请求／尝试去重，不把 run.all_messages 多次读取的同一响应重复累加。保留现有 report.*／tool.*／execution.* 规则指标，分析“缓存省的钱是否被报告重试抵消”。

压缩、模型／规则／工具改变、历史编辑、TTL 间隔标为已知边界；服务商缺报、冷启动和不明丢失分别记录。出现零命中时先检查是否有足够稳定前缀与有效观测；只有此前命中过，才谈“命中突然下降”。

可参考 [Pydantic WarnOnCacheBusts](https://github.com/pydantic/pydantic-ai/blob/b9589436a6fe5a5b614ccf362ebd2b714dd33443/docs/harness/warn-on-cache-busts.md) 的原因分类；暂不安装 Harness。它的“已建立缓存后下降”告警不能替代本项目冷启动／从未命中监测，短命 Agent 也不能承担跨轮统计状态。

## 8. guard 与执行事实的边界

本设计沿用 [2026-10-06 守卫限权与按规则计数](../../2026-10-06-守卫限权与按规则计数.md) 的状态，不能以“Pi 架构重构”为由恢复此前二十多个报告阻断点。

- 报告七个闸门：report.object_unknown、report.number_unmatched、report.range_whole_partial、report.prosody_untraced、report.calc_other_target、report.calc_quantity_mismatch、report.evidence_unknown。
- 七项既有自动修继续自动修：引证补齐／清理、不可核对／残缺推导标注、内部标记清理、coverage 修复、正文过短说明。
- 工具侧维持 schema 校验、唯一目标匹配、用户指定编号／名称、范围策略和 Praat 脚本要求；拒绝提案不当成已执行失败。
- 按真实投递日志区分 not_delivered／not_executed、failed、unknown／blocked；缓存、摘要、续写或会话恢复不得重置未知结果状态，也不能重放已投递操作。

skill 负责解释“应该如何做”，guard 负责核对现有有阻断权的规则，执行器负责真实投递与事实。不新增依赖另一模型判断的 guard，不把文风要求升级成报告闸门。prosody_untraced 是否降级仍由既有规则数据与后续决策处理，本设计不修改它。

### 8.1 与现有逃逸阶梯的兼容约束

Pi 式会话／请求阶段是内部组织方式，L0–L4 仍由现有业务路由控制，不新增一级。L0 专用执行、L1 有限纠正使用规划阶段；L2 独立证据分析、L3 原始材料分析使用各自输入配置的报告阶段；L4 根据入口走普通概念对话或一般分析。允许按目标／能力直接进入适用模式，不要求依次经过所有层级。

阶段配置和消息链可分开，**本轮请求／工具总预算、同一执行问题的失败计数、停滞计数、投递事实和原目标绑定必须共享**。L0→L1→L2→L3、加载 skill、重建 Agent 或压缩历史均不能重置这些状态。显式用户继续仍沿用既有新轮次语义和预检，不因缓存复用偷偷延续或追加执行额度。

一次有区别的执行纠正、同问题再次执行失败退出、连续两轮无新增有效证据退出、永久依赖缺失直接退出、结果 unknown 后停止投递等条件继续沿用。执行前提案错误仍按现有 SDK 工具重试／去重／总预算管理，不冒充已执行失败。L2–L4 不重新注册失败分支的执行工具。

缓存命中的输入仍占上下文，每个实际模型请求仍计入总次数；缓存统计不能改变预算口径。改进后的实际输入更少，可能推迟由上下文不足引起的收尾，但收尾预留、取消和总次数上限继续有效。有限上下文模式的阶段报告／用户点击继续，以及未限制模式的能力检查／自动材料分析，保留现有交互语义；阶段切换不保证整段缓存复用。

文件名候选进入材料元数据，不调用 AnalysisState.add_evidence，不增加测量证据数量，不清零失败／停滞计数，不单独把 coverage 标为 complete。它可以帮助 L0 理解目标、L2 解释测量、L3 对照可能的内容、L4 提供有条件的一般讨论；不能代替词典／对齐依赖、真实音频输入或声学测量，也不能因提供文件名就自动进入 L3。

## 9. 实施顺序与代码边界

| --- | --- | --- |

| 2：请求与对话基础 | 静态阶段配置、规范消息序列化、ModernStore 增量迁移、dialogue 原生追加 | 三轮请求前缀稳定，正式消息不重复；旧会话可读取 |
| 3：任务阶段与预算 | planner／report 原生消息、证据投影、统一预算、压缩版本、修正／续写边界、文件名线索回退 | 工具配对与投递事实可恢复；压缩不损失核对依据；文件名候选可追溯且服从用户说明 |

阶段 5 的连接部分在阶段 2 稳定后即可独立实施；显式缓存依赖最终请求构造与观测完成。每阶段可单独回退，旧数据不删除，不要求同时切换模型／SDK版本／UI框架。

## 10. 验证与验收

先用离线 SDK 替身／本地 HTTP 服务验证结构与行为，再用同一真实模型比较性能。结构通过不代表云端命中已证明。

### 10.1 必须通过的行为

1. 同配置三轮普通对话，前一轮规范历史在下一轮完整保留，当前目标仅追加；最终请求不是单 user 内的 JSON 历史。
2. 规划中 assistant tool calls 与 tool returns 配对、顺序固定；取消／恢复无孤立调用、无未知结果重投。
3. 静态 system／schema／工具顺序在目标和证据变化时不变；技能正文按需追加一次，迁入 skill 不增加模型往返。
4. 普通对话正常完成仍一请求，明确时长快路仍零模型请求；原有工具／报告请求及重试上限不扩大，只有现有恢复流程或必要压缩有额外调用。
5. 压缩保留原证据和近期完整事务，标记新版本；不足时明确失败，旧记录可读。
6. 七项闸门／七项自动修和工具规则回归通过；原目标、范围、来源、单位、delivery unknown／blocked 行为保持。
7. 客户端跨轮复用，换配置／关闭后释放；不同会话的取消不互相影响，Praat 操作维持共享锁与串行语义。
8. usage 缺失／总输入含缓存／总输入不含缓存／重复读响应四种情况统计正确；不暴露凭据和音频原始字节。
9. 无词典且用户未说明时，明确文件名可提供带来源的候选；通用／歧义文件名不强行猜测。已有词典或用户说明时不启用回退；后续用户纠正优先，多个文件不串线，临时导出名不替代原始名称；此流程不增加模型请求或改变静态前缀。
10. L0／L1／L2／L3 切换与压缩不重置本轮总预算或执行状态；缓存 token 仍计入上下文。文件名候选不增加测量证据／重置停滞／单独完成交付；依赖缺失与音频能力不足仍按原阶梯处理。

测试集中在最终请求协议、持久化恢复、预算、取消／投递和统计这些高价值边界；不为每份提示词逐字写镜像测试。沿用现有相关套件完成回归，环境问题单独报告。

### 10.2 真实性能对照

选择五组固定任务：三轮普通概念对话、同对象多参数测量、明确韵律分析、执行失败后报告收尾、长对话接近压缩阈值。每组包含初次请求和至少两次连续追加；A为现有实现、B为改造实现，交替运行并重复，显式／隐式另列。

固定模型／地域／思考档／音频／输出预算，使用隔离会话与记录好的对象／证据。缓存状态和请求间隔写入结果；冷／热状态不能准确控制时如实标为观察值，不把相邻运行自动称为公平冷启动。长历史压缩前后单列。

对照项：各阶段输入 token 与重复量、缓存读／写／覆盖率、真实费用、首字与整任务耗时中位数／范围、请求次数、工具时间、报告重试、guard block／repair。费用按测试当时官方模型价与实际 usage 算，不把缓存读折扣统一套所有模型。

性能验收按可验证条件决定：没有新增不必要往返；重复历史／证据减少；具备可观测缓存时连续请求的读缓存与总费用改善；运行时间没有被额外技能加载／全局排队抵消。低于缓存门槛或字段缺报的任务只验结构／耗时，不声称命中改善。具体幅度由测量报告给出，**不预承诺 85% 命中率或固定倍数提速**。
