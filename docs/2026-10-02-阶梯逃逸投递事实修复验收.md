沙箱只是「谁来启动」；真正让 Praat 一定是 Low 的是**映像文件的标签**：

| 检查 | 结果 |
| --- | --- |


## 2. 三层根因

### 2.1 环境（不改代码，只需换一个正常启动的实例）

沙箱里的前端无法写 Praat 的消息文件。`Praat.exe` 与 `python.exe` 都是 Low 完整性，
`sendpraat.deliver()` 的 `path.write_text()` 直接 EACCES。

### 2.2 产品：把「根本没送出去」当成「执行状态不明」（真 bug）

按设计 §3，「执行超时且**是否执行不明**」才需要停下来核实；「未执行」（脚本没送出去）
属于确定的失败，应当按 L1 给一次有区别的修正，并且**不影响同一轮后面的其它操作**。
原实现把两者混成一种：

1. `cloud_workflow.execute()` 只要 `chat._send_script()` 返回 False，就 `execution_unknown = True`，
   之后**整轮所有投递**都被 `'此前执行状态不明，本轮禁止继续投递'` 挡住。而 `_send_script`
   的返回值分不出「消息文件写不进去」（什么都没跑）和「交出去了没等到完成标记」。
2. 这条快照导出发生在阶梯开始**之前**（`prepare_audio` 的预导出），于是模型第一次工具调用
   （`vot`）就被这条闸门拒绝。
3. `cloud_agent` 又按**说明文字**猜状态：那句拒绝语里含「状态不明」→ 被记成 `unknown` →
   `permanent=True` → 立刻 `BranchExit`，连一次修正机会都没有。
4. 报告上下文里只有 `missing_reason`（=那句拒绝语）和 `paused_branches`；真正的
   `Message.txt` 权限原因只留在 `state.attempts` 里，**没进报告请求**，于是模型只能自己编一个
   理由（「模型不支持音频」）。
5. 顺带发现：音频能力关闭时（本机 `qwen3.7-flash` 预设就是关闭）那份快照**永远不会被用到**
   （`report()` / `should_escalate_audio()` 都先看 `audio_input_enabled`），却照样花掉一次投递。
6. 顺着这次现场还看到两个**既有**小毛病（本次没改，见 §7）：`vot` 自动估计那条路跑完会留下
   一个 `Harmonicity` 派生对象（工具只删自己的临时 Sound/Intensity）；报告只拿到
   「原因」最后一句话时容易自己编理由。

## 3. 改了什么

新增 `ai/praat_ai/delivery.py`（唯一一份投递事实词汇：`DELIVERED` / `NOT_DELIVERED` /
`EXECUTION_UNKNOWN` / `EXECUTION_BLOCKED`），四个文件按它对齐：

| 文件 | 改动 |
| --- | --- |
| `delivery.py` | 新增。说明四种投递事实的区别，供 `chat` / `cloud_workflow` / `cloud_agent` 共用，避免再靠文字串猜 |
| `chat.py` | `_send_script(..., outcome=[...])` 这个可选出口写回「到底送出去没有」；`_send_script_via_argv` 同样处理（`Popen` 失败 = 没送出去）。不传 `outcome` 的调用方行为不变 |
| `chat.py` | `AgentStep.execution` 新字段（默认 `''`）：把投递事实带出执行层，调用方不用看说明文字 |
| `cloud_workflow.py` | `execute()` 只在**真的交出去但没等到完成**时置 `execution_unknown`；「没送出去」返回确定的失败并说明「Praat 没有收到这条指令」；闸门关闭时的拒绝语不再含「状态不明」，并按 `EXECUTION_BLOCKED` 带出；`prepare_audio` 的尝试记录也带 `execution` |
| `cloud_workflow.py` | 预导出快照只在 `config.api.audio_input_enabled` 为真时才做（用不上的材料不花投递） |
| `cloud_agent.py` | `tool()` 先看 `step.execution`：`unknown` 只给「交出去没等到完成」；`not_delivered` 是普通失败（允许一次修正）；`blocked` 记 `not_executed` 并停止投递。`execution` 为空（外部替身/本地工具）时才退回按文字判断——老行为对自定义执行器仍然保守 |
| `cloud_agent.py` | `blocked_attempts(state)`：把失败/状态不明/未执行的尝试去重后进报告上下文（原来只有 `missing_reason`，装不下真正的原因）；`report_context()` 新增 `blocked_attempts` 并纳入压缩路径 |
| `cloud_agent.py` | `report_instructions(config, state)`：**只有本轮真有失败记录**（`failures` 或 `blocked_attempts`）时才追加 `FAILURE_INSTRUCTIONS`（如实交代失败原因与下一步、不得把投递/环境故障写成模型能力不足、`audio_input=false` 不等于无法测量）。预检 `minimum_continuation_tokens()` 与真实报告共用这一个入口，避免两边不一致 |

提示词开销是按需付的：2048 上下文那类紧预算用例在**没有失败**时和改前逐字节等价（见 §5 的两个红→绿用例）。

## 4. 用户可见的变化（同一个故障再发生时）

- 不再出现「测量失败：此前执行状态不明，本轮禁止继续投递」这种一步锁死整轮的话；
- 快照导出失败后，`vot` 仍会被**真的投递**；在正常环境里就能测出数值；
- 如果连 `vot` 也送不出去，报告会写「脚本没有投递给 Praat（Praat 没有收到这条指令）：无法写入
  Praat 消息文件（…）：[Errno 13] …」，并给出下一步，而不是说「模型不支持音频」；
- 真的超时/完成标记对不上时，行为不变：停止投递 → 用已有证据收尾，并带上超时原文。
