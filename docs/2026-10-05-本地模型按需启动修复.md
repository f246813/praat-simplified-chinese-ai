# 本地模型连接拒绝修复

现场：本地配置指向 `http://127.0.0.1:8000/v1`，配置中的 llama-server 和 GGUF 文件均存在，但无服务监听，`server.auto_start=false`。现代窗口启动仅打开 UI，而 `LocalResources.lease` 沿用旧 auto_start 判断并跳过启动，随后正式任务请求直接返回 WinError 10061。上一次 Message.txt 权限修复仍有效，这次故障发生在模型连接阶段。

修改 `ai/praat_ai/modern_app.py`：

- 本地任务地址为回环地址、端口匹配配置，且已填写 llama-server 与模型路径时，在任务使用模型前通过已有 QwenServerManager 按需启动并等待就绪。
- auto_start 仅在管理器的配置副本中启用，保留用户磁盘配置及任务参数；无本地启动配置或其他端口的外部服务保持原有连接方式。
- “测试连接”共用相同的本地资源占用与启动逻辑。加载失败时不发送模型请求；云端仍走原有路径。
- 继续沿用现有串行资源调度、模型复用和仅停止自有服务的机制。

GitHub 插件检索了 abetlen/llama-cpp-python 的 ensure_started/auto_start（无合适结果），以及 ggml-org/llama.cpp 的启动加载实现：
https://github.com/ggml-org/llama.cpp/blob/e117148a41d8e9bedb72e4c6c3f003ab0fe7f857/tools/server/server.cpp

没有搬入新的第三方代码或依赖。实际复用本项目 `QwenServerManager.ensure_started`、服务就绪检测和 `LocalResources` 调度；现有许可保持不变。GitHub LICENSE 拉取出现连接错误，因此不把未取回的许可内容作为本次新增代码来源。

验证：

- 三项新增回归先在旧实现上失败，确认漏启动和测试连接绕过资源管理。
- modern_app、modern_execution、api_transition、model_progress 共 95 项测试通过。
- 实机使用用户配置的副本、真实本地模型和独立临时数据目录。为最小回复测试，仅在副本关闭思考：冷启动、连续请求复用 PID、停止后切回本地重新启动全部 verified。记录见 `installer/verification/local-model-start.json`。
- 第一次原参数实测已成功启动并请求模型，但“高思考强度＋700 token”导致回复截断。这是另一项输出预算限制，没有静默修改用户配置。
- 用户配置哈希保持不变；用户 Praat 会话保留；验证创建的模型服务已通过自身管理器关闭，没有重放用户失败任务。
